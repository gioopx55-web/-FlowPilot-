### D-035 — Phase 7 contrast audit results: 4 token adjustments made
**Date:** 2026-10-04
**Decision:** Performed the D-034 audit against real rendered Dashboard elements (badges, text, links, focus rings), using the browser's own canvas color compositing rather than regex-parsing computed-style strings (an earlier version of the audit script silently mis-parsed Tailwind v4's `oklab()`/`color-mix()` output and produced false readings — the final method renders each color via `<canvas>` and reads back resolved pixels, which cannot misparse). Four tokens adjusted, smallest-change-that-clears-AA in each case:
- `--fp-success` (light): #0f9d58 → #0a6b3c (badge text was 3.13:1 against its own tint bg, now 5.68:1)
- `--fp-warning` (light): #b54708 → #a84007 (was 4.38:1, now 4.99:1)
- `--fp-danger` (light): #d92d20 → #b3251a (was 3.89:1, now 5.29:1)
- `--fp-accent` (dark): #6e7cf2 → #8591f5, with `--fp-accent-hover` nudged to #9da7f7 to stay a visible step lighter (badge text was 4.35:1, now 5.49:1; this also strengthened the already-passing dark-mode link contrast from 5.39:1 to 6.82:1)
- Focus ring opacity: `ring-ring/50` → `ring-ring/70` across all 9 usages (was 2.2-2.3:1 in both themes against canvas, now 3.27:1 light / 3.84:1 dark) — the 50% opacity itself was mathematically the limiting factor regardless of hue, so the fix is the opacity multiplier, not a token hex value
All changes verified in both light and dark themes after the fix. Primary text, secondary text, light-mode accent/info, and dark-mode warning/danger/success/info were already compliant and left unchanged. Full before/after values and reasoning are recorded as comments directly in `src/styles/tokens.css`.
**Why:** Resolves the D-034 checklist. This is not a palette redesign — every adjustment is a minimal shift of one existing token's lightness, chosen by computing the smallest change that clears the relevant WCAG threshold.

### D-036 — Shared not-found guard for project-scoped routes; not-found.tsx placement corrected
**Date:** 2026-10-04
**Decision:** Every project-scoped entry point (the `[projectId]/layout.tsx` and all four tab components — Overview/Tasks/Team/Activity) calls one shared `requireProject(projectId)` guard (`components/projects/requireProject.ts`) that calls Next's `notFound()` for an unknown ID. `src/app/(app)/projects/not-found.tsx` lives in the *parent* `projects/` segment, not inside `[projectId]/`.
**Why:** Found via Phase 8 visual verification: an invalid `projectId` rendered a silent blank page (no crash, no message) with a server-side error logged (`getProjectRisk: unknown projectId "..."`). Root cause had two parts — (1) Next.js App Router only lets a segment's own `not-found.tsx` catch `notFound()` calls from that segment's *children*, not from the segment's own layout, so it was rendering the *root* `app/not-found.tsx` instead of a project-specific message; (2) Next can render a layout and its page concurrently, so the layout alone calling `notFound()` did not reliably stop a child tab component from independently calling a selector that throws on an unknown ID. Both are now fixed structurally (guard called everywhere; not-found.tsx in the correct segment) rather than patched case by case. **Binding on any future nested dynamic route** (e.g. a future `/clients/:clientId/...` or `/team/:memberId/...` detail section) — use the same `requireProjectId`-style guard-in-every-entry-point pattern, not a layout-only check.
**Known limitation (not fixed, documented):** the not-found response returns HTTP 200, not 404, because the `(app)/loading.tsx` Suspense boundary (Phase 5, D- already approved) begins streaming the response before the nested `notFound()` fires. Content is correct; only the HTTP status is affected. Not pursued further — fixing it would require revisiting the Phase 5 streaming/loading-boundary architecture for a dev-tooling/SEO nicety with no user-visible impact in a demo app with mocked auth.

### D-037 — `npm test` was silently running only 1 of 5 test files since Phase 6
**Date:** 2026-10-04
**Decision:** `package.json`'s `test` script changed from `node --import ./scripts/alias-loader.mjs --test src/**/*.test.ts` to `find src -name '*.test.ts' | xargs node --import ./scripts/alias-loader.mjs --test`.
**Why:** Found during Phase 8: npm executes package.json scripts via `sh`, which does not support bash's `globstar` (`**`) — the glob silently degraded to matching only `src/domain/selectors.test.ts` (the one file exactly one directory level deep in a way the degraded pattern happened to match), while `followUp.test.ts`, `risk.test.ts`, `workload.test.ts`, and `index.test.ts` were never actually executed by `npm test`, despite every prior phase's final report claiming "N/N passing." Running the test files explicitly (as done manually during Phase 6/7 verification) always worked correctly — only the `npm test` convenience script was affected. `find | xargs` is shell-portable and was verified to correctly discover and run all 5 files (43 tests). **No evidence any previously-reported passing test was actually failing** — spot-checked by running all 5 files explicitly before this fix, which also passed — but this should have been caught sooner, and is logged so a future session doesn't trust an `npm test` pass without also confirming the discovered test count looks right for the number of `*.test.ts` files that actually exist.

### D-039 — V1 demo-state/persistence architecture: server-side in-memory overrides
**Date:** 2026-10-04
**Decision:** Task edits (Kanban drag, `StatusSelect`, Task Detail form) are recorded in a module-level, server-side, in-memory "overrides" map (`domain/taskMutations.ts`), keyed by task ID, applied on top of the unchanged Phase 6 base fixtures at every `getDemoDataset()` call (`data/mock/index.ts`). This is **process-lifetime** state in the Node process running `next dev`/`next start` — explicitly NOT localStorage and NOT a per-browser/client store. It resets when the server process restarts, and (since V1 has no real auth or multi-tenancy) is shared across every browser tab hitting that server instance. Next.js Server Actions (`lib/taskActions.ts`) are the only way the UI reaches these functions, and each calls `revalidatePath("/", "layout")` so every Server Component re-renders with fresh data on next visit — this is what keeps Dashboard/Projects/Tasks/Kanban/Project Detail consistent with zero client-side state-syncing code. `resetTaskOverrides()` provides the "reset to demo data" capability. Base fixture arrays in `data/mock/*.ts` are never mutated.
**Why:** The Phase 9 brief required "one source of truth," consistency across every page without manual syncing, and explicitly allowed (but did not mandate) localStorage — framed as "if local client state/localStorage... document that clearly." Given the codebase's existing heavy use of Server Components (every page since Phase 7 reads `getDemoDataset()` directly, synchronously, server-side), a localStorage-based design would have required converting Dashboard/Projects/Tasks into client-fetching components (since Server Components cannot read browser localStorage), which is a far larger and riskier architectural change than this phase's actual goal. The chosen design reuses the exact singleton-module pattern `data/mock/index.ts` already established in Phase 6, needs no new state-management dependency (no Zustand/Redux), and is honestly documented as process-lifetime, server-shared state — not a real backend, not real per-user persistence, exactly as the brief required ("do not pretend a backend persistence layer exists").
**Known tradeoff (accepted, not a defect):** restarting the dev/prod server process discards all edits (by design — this is a demo, not a database) and all edits are visible to every browser tab hitting the same server (acceptable given no real auth/tenancy exists in V1). If a future phase adds real multi-user auth, this architecture must be revisited — flagged here so it isn't forgotten.

### D-066 — Two real RTL bugs found and fixed: bidi-scrambled numeric summaries, a bare bullet-marker character
**Date:** 2026-10-05
**Decision:** Two genuine (non-cosmetic) RTL defects were found during the Phase 15 visual audit, both confined to Phase 14's Settings additions, both fixed:
1. `src/app/(app)/settings/workspace/page.tsx` and `src/app/(app)/settings/billing/page.tsx` each rendered a stat line of the shape `{count} label · {count} label · {count} label` (e.g. "8 team members · 15 clients · 19 projects"). Under `dir="rtl"`, the Unicode Bidi Algorithm relocated the *leading* number to the visual end of the line (rendering as "…15 clients · 19 projects 8" — i.e. actually scrambled, not merely mirrored). Fixed by wrapping each line in `dir="ltr"` + `[unicode-bidi:isolate]`, the same technical-value-isolation pattern already established for email fields (D-015-era precedent, reused verbatim — no new pattern invented).
2. The Billing capability list used a literal `"· "` text prefix per `<li>` instead of a native list marker. A bare neutral character at the very start of a text node is exactly the case the bidi algorithm handles unpredictably; under RTL the dot visually detached to the wrong edge. Fixed by switching to `list-disc`/logical `ps-4` padding (grep-confirmed as the pattern every *other* bulleted list in the app already uses — `ConditionsDisclosure`, `ProjectOverview`, `AIProjectRiskExplanationCard`, `AIWeeklyReportCard`, `AnalyticsInsights`, `RiskShowcase` — this was the one outlier, not a new pattern).
**Why:** Both are genuine, user-visible scrambling (not the cosmetic, linguistically-correct "trailing sentence punctuation flips to the start" behavior already accepted in D-015/Phase 14 — e.g. a period or "?" moving to the front of an English sentence under a forced RTL paragraph is expected Unicode bidi behavior for prose, not a bug; a *count* relocating past unrelated later counts, or a *list marker* detaching from its item, is not). A full codebase grep (`{[a-zA-Z0-9_.]+\} [a-zA-Z]+( ·| of | assigned| overdue| day)`) confirmed these were the only two occurrences of the leading-raw-number pattern and the only hand-rolled bullet prefix in the app — not a systemic issue requiring a broader sweep.

### D-068 — Mobile sheets were silently rendering at `w-3/4`, not full-screen, since Phase 5
**Date:** 2026-10-05
**Decision:** `SidePanel.tsx` (AI/Notifications), `TaskDetailPanel.tsx`, and `MarketingNav.tsx`'s mobile menu all passed a plain `"w-full sm:max-w-*"` className to `SheetContent` to get full-screen-on-mobile / bounded-width-on-tablet-desktop behavior. This never worked below the `sm` (640px) breakpoint: the base `sheet.tsx` primitive's own classes include `data-[side=left]:w-3/4 data-[side=right]:w-3/4` unconditionally, and a Radix `data-*` attribute selector carries higher CSS specificity than a plain utility class of otherwise-equal weight — so the primitive's `w-3/4` always won below `sm:`, regardless of what the consumer's `className` prop said. Confirmed empirically: `getBoundingClientRect().width` measured exactly 75% of viewport width at 320px/390px, correctly reaching `max-w-sm`/`max-w-lg`/`max-w-xs` only once the `sm:` breakpoint also added `data-[side=...]` prefixes with the viewport-reported widths. All three were fixed by matching the same `data-[side=left]:w-full data-[side=right]:w-full sm:data-[side=left]:max-w-* sm:data-[side=right]:max-w-*` syntax — same specificity tier as the primitive's own classes, so the override actually wins.
**Why:** This is a real, silent, product-wide defect found during Phase 16's responsive audit — the AI Assistant panel, Notifications panel, and Task Detail panel have been rendering at 3/4 width on every phone-sized screen since Phase 5 (with the underlying page visible and interactive behind a dim overlay to one side), directly contradicting Phase 5's own approved "full-screen sheet" mobile design and multiple later phases' docblocks that explicitly claimed this behavior without it ever having been true. The fix is a CSS-specificity correction, not a new pattern or new architecture — **binding**: any future Sheet consumer that needs a mobile-vs-desktop width split must use the `data-[side=...]:` variant form, never a plain `w-*`/`max-w-*` override, or it will silently lose to the primitive's own classes exactly the same way.

### D-071 — Non-modal panels never restored focus to their trigger on close; fixed with a self-managed focus snapshot
**Date:** 2026-10-05
**Decision:** The AI Assistant panel, Notifications panel (both via `SidePanel.tsx`), and the Task Detail panel (`TaskDetailPanel.tsx`) all dropped keyboard focus to `<body>` when closed via Escape, instead of returning it to whatever triggered the panel open. Confirmed via real click-then-Escape interaction (not a scripted direct-URL-navigation test, which doesn't exercise the actual focus-capture moment) that all three panels now correctly return focus to their trigger. **Binding**: any future non-modal panel, or any modal opened by something other than a Radix `Trigger`, should use this same self-managed snapshot-and-restore pattern rather than assume Radix handles it.

### D-072 — Settings/Client/Project tabs were using `role="tablist"`/`role="tab"` for real route navigation; corrected to `aria-current="page"`
**Date:** 2026-10-05
**Decision:** `SettingsTabs.tsx`, `ClientTabs.tsx`, and `ProjectTabs.tsx` all applied `role="tablist"` to their `<nav>` and `role="tab"`/`aria-selected` to each `<Link>`, despite every "tab" being a genuine, separately deep-linkable route (not an in-page panel switcher) — `ProjectTabs.tsx`'s own docblock already said as much ("real navigation links, not a client-state panel switcher") while its markup contradicted it since Phase 8. The ARIA tab pattern commits to specific behavior screen readers rely on — arrow-key navigation between tabs (not Tab), `aria-controls` pointing to a same-page `tabpanel` — none of which this component actually implements, since each click performs a real navigation. Fixed by removing the tab roles entirely and adding `aria-current={active ? "page" : undefined}` to the active link — the correct native way to mark "this link represents the current page" within a plain `<nav>` landmark (which was already correctly labeled and is kept as-is).
**Why:** Phase 17 §13 explicitly named this exact scenario ("If route navigation is semantically links, do not force ARIA tab semantics unnecessarily"). A screen reader encountering `role="tab"` announces "tab, 1 of 5" and sets an arrow-key-navigation expectation that silently fails here, which is more confusing than no ARIA role at all. **Binding**: any future route-backed tab-styled navigation should follow this `aria-current="page"` pattern, not the ARIA tab pattern — reserve `role="tablist"`/`role="tab"` for a genuine in-page panel switcher if one is ever built.

### D-073 — Analytics chart `aria-hidden` containers held focusable content; Recharts' own accessibility layer disabled

### D-080 — A real, pre-existing bug: every marketing glow/backdrop layer has been invisible since Phase 13.5/13.6
**Date:** 2026-10-05
**Decision:** While implementing Phase 17.6's glow/depth upgrades, every negative-`z-index` decorative layer on the public site (the Hero's ambient glow, the AI section's glow, the Final CTA's glow, every `tone="surface"` showcase's `DotGrid` backdrop via `ShowcaseLayout`, the Dashboard showcase's `DotGrid`, and the Login page's radial glow) was found to be rendering with **zero visual effect** at any opacity — confirmed by testing with an extreme, unmistakable 35% solid `rgba()` fill, which still produced no visible paint. A `-z-10` descendant with no local stacking context escapes to the nearest ancestor that has one — here, none did — so the layer stacked at the document root, *below* the page's own normal-flow canvas-colored background `<div>`, rendering it permanently hidden regardless of color or opacity. Confirmed fixed via direct computed-style/bounding-rect inspection plus before/after screenshots showing a real, visible glow for the first time.
**Why:** This was discovered, not manufactured — the task was to upgrade glow/depth quality, and the existing glow was already always this `--fp-accent-subtle-bg` pale, nearly-indistinguishable-from-canvas color (a deliberate, restrained choice per Phase 13.5/13.6), which made the complete absence of any visible effect easy to mistake for "very subtle by design" rather than "not rendering at all" in every prior phase's visual QA. It only surfaced once a much stronger test color still produced nothing. This single fix is responsible for most of this phase's visible quality jump — every section's intended depth layer (dot-grid backdrops, the Hero/AI/CTA glows, the layered card-behind-card effect) is now actually visible for the first time since it was built. **Binding**: any future `position: relative` container with a negative-`z-index` decorative child must also carry `isolate`, or the layer will silently fail to render exactly this way.

**Phase 21.3 supersession note:** D-102 replaces the project-only validation description with complete shared runtime validation for every mutation family. D-103 replaces stale-session handling: AI actions are now guarded, missing action sessions redirect visibly from the action boundary, and Proxy passes `next-action` POSTs through to that guard. D-097's contrast fix and its security findings remain valid.

### D-098 — Soft 404 fixed cleanly (loading.tsx was the root cause); a committed dev-only QA harness closes the "no reproducible browser audit" gap
**Date:** 2026-10-06
**Decision:** Phase 21.1 §6 (release blocker: the D-036 known limitation that invalid-entity routes return HTTP 200 instead of 404) was root-caused, not just re-documented: a single `src/app/(app)/loading.tsx` wrapped **every** route under `(app)/*` in one shared Suspense boundary, forcing Next.js to flush a 200 status immediately on navigation, before a deeper `notFound()` call (in `[projectId]`/`[taskId]`/`[clientId]`/`[memberId]`) could ever change the response status — by the time `notFound()` resolved, the 200 header was already sent and irreversible. Removing that one file (confirmed via a live production build + browser test) immediately fixed real 404 status codes on all 4 invalid-entity routes, with **zero navigation regression**: this app's entire data layer is synchronous in-memory (D-039), so the route-transition loading skeleton the file provided was never load-bearing against real network latency, and client-side navigation between list pages was re-verified smooth with it removed. No architecturally-churny per-segment `loading.tsx` restructuring was needed (the originally-expected harder path) — the fix was a clean deletion, not a forced one, and the brief's "do not spend disproportionate effort fighting framework streaming semantics" caution turned out not to apply once tested. Phase 21.1 §15/§16 (release blocker: the independent audit "could not reproduce the full axe matrix" — no committed, reproducible browser-QA path existed) added a small dev-only harness at `qa/` (`axe.mjs`/`responsive.mjs`/`rtl.mjs`, a shared `qa/routes.mjs` route matrix, `npm run qa:axe`/`qa:responsive`/`qa:rtl`/`qa:all`): `playwright` added as a devDependency (explicitly pre-approved by the brief for exactly this purpose); `axe-core` used via plain Node module resolution against the copy already present transitively (via `eslint-plugin-jsx-a11y`/`eslint-config-next`, the same reuse Phase 17's D-070 relied on) rather than declared as a second new dependency — if a future `eslint-config-next` upgrade ever drops it, the script fails loudly with a clear message rather than silently skipping. Not a new E2E framework: three short, focused scripts, no test runner, no CI wiring, README-documented commands only. Full results (all clean after D-097's contrast fix): `qa:axe` — 0 serious/critical violations across 15 routes × light/dark (30 checks); `qa:responsive` — 0 horizontal overflow across 13 routes × 6 viewports (320/390/768/1024/1280/1440), correct AI-panel docking at every breakpoint (full-width mobile per D-068, below-Topbar desktop/tablet per D-085); `qa:rtl` — 0 overflow across 5 representative routes under forced `dir="rtl"`, Sidebar confirmed docking to the physical right (inline-start).
**Why:** Both items share a root cause of "architecture assumed correct without being re-tested" — the loading.tsx 200-status bug and the missing QA harness. ### D-101 — One typed process-global demo store supersedes module-local mutable stores
**Date:** 2026-10-06
**Decision:** `domain/demoStore.ts` is the sole owner of mutable business demo state, initialized once at `globalThis.__flowpilotDemoStore`. It owns task/client/project/user overrides, added client interactions/projects and their counters, notification preferences, and notification read IDs. The storage-implementation portion of D-039/D-062/D-094/D-095 is superseded: those domain behaviors remain, but no mutation family owns a private module-local Map/Set/array/object. The module is `server-only`; client-safe AI intent contracts were separated from server matching logic after the production build correctly exposed an accidental client import chain.
**Why:** Next.js production compilation can emit the same source into separate server bundles. Module scope is singleton only per loaded bundle, not per Node process; `globalThis` is common to those bundles and therefore supplies deterministic action-to-render consistency without adding infrastructure outside the approved demo scope. This is intentionally process-lifetime, shared across all visitors in that process, non-durable, and not account-isolated. A multi-process deployment would require real shared persistence and is outside V1.

### D-102 — One reset plus dependency-free runtime validation for every mutation family
**Date:** 2026-10-06
**Decision:** `resetDemoDataAction()` now calls only `resetDemoStore()`, which clears/reinitializes every mutable family. `domain/runtimeValidation.ts` supplies small runtime guards reused across tasks, clients/interactions, projects, profile/preferences, and notifications. Payloads are checked for object shape, allowed keys, bounds, types, enums, date/email formats, and valid fixture references before writes; invalid values return the existing safe `{ ok: false, error }` contract. The suite now contains 192 tests, including every malformed input independently demonstrated in Phase 21.2 and an all-families reset test.
**Why:** TypeScript does not validate serialized Server Action input. One small native validation layer avoids a dependency while closing the actual trust-boundary gap, and one store-level reset prevents a new state family from being forgotten by an orchestration list.

### D-103 — Expired Server Action sessions redirect visibly through the action boundary
**Date:** 2026-10-06
**Decision:** `requireDemoSession()` redirects to `/login?reason=session-expired` when the cookie is absent. Proxy continues protecting ordinary app navigation, but passes protected `POST` requests carrying the `next-action` header to the independently guarded action so Next.js can encode the redirect correctly in the action response. Login displays the reason. AI Server Actions are guarded too, leaving only sign-in/sign-out exempt.
**Why:** Phase 21.2 confirmed mutation rejection but also confirmed a stale page could fail without useful feedback because Proxy intercepted the action POST as an ordinary navigation. Action-aware redirect handling produces a recoverable, visible UX while retaining defense at every callable Server Action.

### D-104 — Production mutation E2E is a release gate; QA matrix covers open workflows
**Date:** 2026-10-06
**Decision:** `qa:production` is the regression for the precise production bundling failure: create/edit project, related views and AI, task mutation, notification preference/read persistence, reset, and expired-session handling across navigation and refresh on `next build --webpack` + `next start`. `qa:all` remains the single axe/responsive/RTL entry point and now opens onboarding, Notifications, and AI and includes Project forms plus the required route/workflow matrix. `qa:routes` covers every implemented page and real 404s. Phase 21.3 is classified **A. READY TO DEPLOY AS V1 DEMO**, with no deployment performed.
**Why:** Domain tests cannot detect duplicated production bundle state. A release claim for this architecture now requires observable Server Action → subsequent Server Component render behavior under the production runtime, not dev-server behavior or imported-function tests alone.
